# 検証・PoC向け公開サーバーセキュリティガイドライン

このガイドラインは、WebサーバーやAPIサーバーなどを、検証・PoC目的で一時的にインターネットへ公開する際の最低限の対策を定める。

具体的なコマンドは [Security Cook Book](./cook-book/README.md) を参照する。過去の事例は、[公開サーバー運用から学ぶ重要サイバー攻撃事例](./incident-cases/IMPORTANT_CYBER_INCIDENTS.md) を参照する。

本番環境、長期間の公開、個人情報・顧客情報・機密情報を扱うサーバーは対象外とし、別途、本番向けの基準を適用する。

## 1. 想定する利用方法

- 技術検証やデモのため、短期間だけ公開する
- 利用者や接続元がある程度限定されている
- 失われても再作成できるデータだけを扱う
- 個人情報、顧客情報、本番データ、重要な認証情報を保存しない

上記を満たさない場合は、PoCであっても本番相当のセキュリティ対策を検討する。

## 2. 最低限行う対策

公開前に、次の対策を必ず行う。

| 対策 | 実施内容 |
| --- | --- |
| 管理者の明確化 | 誰が作成し、誰が停止・削除するかを決める |
| 公開期限 | 公開終了日を決め、利用後に放置しない |
| ファイアウォール | 受信通信を原則拒否し、必要なポートだけ許可する |
| SSH制限 | SSHは接続元IP、VPN、踏み台などで制限する |
| 安全な認証 | SSH公開鍵を使用し、`root`の直接ログインや初期パスワードを使用しない |
| ソフトウェア更新 | 公開前にOSと利用ソフトウェアを更新する |
| HTTPS | Web画面やAPIを公開する場合は、原則としてHTTPSを使用する |
| 秘密情報の分離 | パスワードやAPIキーをソースコードへ埋め込まない |
| 最低限のログ | SSH、Webサーバー、アプリケーションのエラーログを確認できるようにする |
| 利用後の削除 | サーバー、DNS、許可ルール、鍵、保存データを削除する |

## 3. ネットワークとファイアウォール

受信通信は原則拒否とし、検証に必要な通信だけを許可する。

| 用途 | 公開方針 |
| --- | --- |
| HTTPS | Web画面やAPIの公開に必要な場合だけ許可する |
| HTTP | HTTPSへの転送や証明書発行に必要な場合だけ許可する |
| SSH | 全体公開せず、管理者のIPアドレスやVPNからだけ許可する |
| データベース | インターネットへ直接公開しない |
| 管理画面 | 可能な限り接続元を制限し、認証を必須にする |

- クラウド環境では、セキュリティグループなどのクラウド側ファイアウォールを設定する
- OSのホストファイアウォールも有効にする
- IPv4だけでなくIPv6側の公開状態も確認する
- 一時的に追加した許可ルールは、検証終了時に削除する
- 使わないサービスや待受ポートは停止する

WAF、CDN、高度なDDoS対策は必須としない。ただし、不特定多数へ公開する場合や大量アクセスが想定される場合は利用を検討する。

## 4. SSHと管理者アカウント

- 管理者ごとに個別アカウントを使用する
- SSHは公開鍵認証を使用する
- `root`での直接ログインを禁止し、必要な操作だけ`sudo`を使用する
- パスワード認証を無効化する場合は、公開鍵で接続できることを別セッションで確認してから変更する
- 秘密鍵は共有せず、パスフレーズで保護する
- 不要になった管理アカウントと公開鍵は削除する

SSHのポート番号変更だけでは十分な対策にならない。接続元制限と公開鍵認証を優先する。

## 5. OSとソフトウェア

- サポート期間内のOSとソフトウェアを使用する
- サーバー公開前にセキュリティ更新を適用する
- 検証期間が長くなる場合は、期間中も定期的に更新する
- 不要なパッケージ、サンプルアプリケーション、デバッグ機能を無効化する
- 外部のインストールスクリプトをそのまま実行せず、提供元と内容を確認する

短期間の検証でも、重大な脆弱性が公表された場合は、更新、公開停止、接続元制限のいずれかを速やかに行う。

## 6. アプリケーション、HTTPS、秘密情報

- アプリケーションを`root`権限で実行しない
- データベースやキャッシュはローカルまたは内部ネットワークからだけ接続可能にする
- 初期アカウント、初期パスワード、デバッグモードを無効化する
- 認証が必要な画面やAPIを、認証なしで公開しない
- HTTPSを使用し、証明書エラーを放置しない
- パスワード、APIキー、秘密鍵をGitリポジトリやコンテナイメージへ含めない
- 検証用の権限は必要最小限とし、本番環境や本番データへ接続できないようにする
- ログへパスワード、トークン、個人情報を出力しない

実在する個人情報や顧客情報の代わりに、ダミーデータを使用する。

## 7. 最低限のログと確認

高度な監視基盤や24時間対応は必須としないが、問題発生時に状況を確認できるよう、次のログを有効にする。

- SSHのログイン成功・失敗
- Webサーバーのアクセスログとエラーログ
- アプリケーションの起動・停止とエラーログ
- ファイアウォールで拒否された通信

検証期間中は、少なくとも次のタイミングでログと状態を確認する。

- 公開直後
- 設定変更後
- 想定外のエラーやアクセス増加があったとき
- 公開終了前

ログの集中管理や長期保存は必須としない。ただし、漏えいや侵入の疑いがある場合はログを削除せず、サーバーを隔離して管理者へ報告する。

## 8. バックアップ

再作成できる検証環境では、複雑なバックアップ運用は必須としない。

ただし、再作成に時間がかかる設定や検証結果がある場合は、次のいずれかを残す。

- Infrastructure as Codeや構築手順
- 設定ファイルの安全なコピー
- 必要最小限のスナップショット
- 検証データのエクスポート

バックアップやスナップショットにも秘密情報が含まれる可能性があるため、アクセス権と削除期限を設定する。

## 9. 公開終了時の対応

検証終了後は、サーバーを停止するだけでなく、不要になった資産を削除する。

- 仮想マシン、コンテナ、ストレージ、スナップショット
- DNSレコード、TLS証明書
- セキュリティグループやファイアウォールの許可ルール
- 検証用アカウント、SSH公開鍵、APIキー
- 検証中に保存したデータとログ

再利用する可能性だけを理由に公開状態で放置しない。再利用時に再作成できる状態を整えた上で削除する。

## 10. 公開前チェックリスト

- [ ] 管理者と公開終了日を決めた
- [ ] 個人情報、顧客情報、本番データを使用していない
- [ ] 必要なポートだけを公開した
- [ ] SSHと管理画面の接続元を制限した
- [ ] SSH公開鍵で接続し、`root`の直接ログインを禁止した
- [ ] OSと利用ソフトウェアを更新した
- [ ] HTTPSを有効にした
- [ ] 初期パスワードとデバッグ設定を無効化した
- [ ] 秘密情報がコード、イメージ、ログに含まれていない
- [ ] エラーや不審なログインを確認できる
- [ ] 検証終了後の削除対象を把握している
