# OSSライセンス利用ガイドライン

## 1. 目的

本ガイドラインは、OSSや無償公開されたソフトウェアなどを業務で扱う際の一次判断と社内手続きを統一し、ライセンス違反や契約上の問題を防ぐことを目的とする。

具体的なライセンスの特徴は[OSSライセンスリファレンス](./OSS_LICENSE_REFERENCE.md)、採用から廃止までの手順は[OSSライセンス運用ガイド](./OSS_LICENSE_OPERATION_GUIDE.md)を参照する。

本ガイドラインは法的助言ではない。対象物のライセンス本文、利用形態、契約、適用法を確認し、判断に迷う場合は法務・知財担当へ相談する。

## 2. 適用範囲

本ガイドラインは、業務で利用、複製、改変、組込み、配布または公開する次の対象に適用する。

- OSSのライブラリ、フレームワーク、ツール、ソースコード
- コンテナイメージ、OSパッケージ、プラグイン、生成コード
- ドキュメント、画像、動画、フォント、データ、データベース
- AIモデル、モデルの重み、学習データ
- API、クラウドサービスのSDK、サンプルコード

## 3. 基本原則

1. **公開されているだけではOSSではない。** OSI承認ライセンスなどによる明示的な許諾が必要であり、ライセンス不明のコードは原則として利用しない。
2. **無料と自由に利用可能は別である。** 無料でも、商用利用、改変、再配布、利用者数などに制限がある場合がある。
3. **ライセンス名だけで判断しない。** 社内実行、社外配布、顧客環境への納品、SaaS、改変、リンクなどの利用形態によって義務が変わる。
4. **ライセンス条件を利用許諾の前提として扱う。** OSSであっても著作権が放棄されるわけではなく、条件の範囲で複製、改変、配布などが認められる。
5. **採用時から記録する。** リリース直前の調査だけでは、推移的依存関係、同梱物、改変履歴、対応ソースを正確に追跡できない。

## 4. 採用時の判断フロー

```text
対象物を採用したい
  ├─ ライセンスと権利者を特定できない → 原則採用しない／法務確認
  ├─ 独自・商用・ソースアベイラブル条件 → 契約全文を確認／法務確認
  └─ 標準的なOSSライセンス
       ├─ 組織内だけで使用 → 告知等を保管。AGPLや契約上の例外も確認
       └─ 組織外へ提供、またはネットワークサービスで使用
            ├─ Permissive → 著作権表示・ライセンス・NOTICE等を同梱
            ├─ Weak copyleft → 対象ファイル／ライブラリとリンク条件を確認
            ├─ Strong copyleft → 結合物を含む対応ソースと同一ライセンスを確認
            └─ Network copyleft → ネットワーク利用者へのソース提供も確認
```

「組織外」には、顧客、委託先、取引先、別法人、一般利用者を含む。グループ会社は別法人であり、当然に社内利用扱いになるとは限らない。秘密保持契約やアクセス制限があっても、ライセンス上の提供該当性が自動的に消えるわけではない。

## 5. 採用前に確認する事項

採用担当者は、少なくとも次を確認する。

- 配布元、権利者、バージョンまたはコミットを特定できる
- `LICENSE`、`COPYING`、`NOTICE`、ファイルヘッダーを確認できる
- SPDX ID、版、`-only`と`-or-later`、例外条項を特定できる
- 直接依存だけでなく、推移的依存と同梱済みコードを把握できる
- 改変、リンク、コピー、同梱、SaaSなどの利用方法が決まっている
- 社内利用、顧客への納品、一般配布などの提供範囲が決まっている
- 必要な表示、ソース提供、変更記録を実施できる

## 6. 法務・知財担当へ相談する条件

次の場合は自動承認せず、採用、公開、納品または提供の前に相談する。

- ライセンスがない、不明である、または権利者や取得元に疑義がある
- 独自ライセンス、非商用、研究限定、競合・用途・地域制限がある
- GPL、LGPL、AGPLなどを独自製品、SaaSまたは機器へ組み込む
- 複数ライセンスの選択条件、互換性、リンク、派生物性に疑義がある
- 特許、商標、暗号、輸出管理、個人情報などのライセンス外リスクがある
- 顧客契約の権利保証、秘密保持、ソース非開示条件と衝突する可能性がある

## 7. 自社コードを公開する場合

- 会社が公開権限を持つことを確認する
- 従業員・委託先の権利帰属、第三者コード、秘密情報、特許出願予定を点検する
- 公開目的に合う既存の標準ライセンスを選び、独自ライセンスを安易に作成しない
- リポジトリ直下に正確な`LICENSE`を置き、必要に応じて`NOTICE`、README、SPDX IDを整備する
- DCOやCLAなどのコントリビューションルール、行動規範、セキュリティ窓口を決める
- 商標の利用条件、サポート、保証の有無をライセンスと分けて明記する

広い再利用を優先する場合はMITやApache-2.0、改変の共有を求める場合はMPL、GPL、AGPLなどが候補になる。会社方針、特許戦略、既存依存物との互換性、ビジネスモデルを踏まえて決定する。
