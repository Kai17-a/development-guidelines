# OSS・ソフトウェアライセンス実務ガイド

## 1. 目的と位置付け

本書は、OSS（オープンソースソフトウェア）や無償公開されたコード、ライブラリ、コンテナイメージ、AIモデル、データ等を業務で扱う際の、一次判断と社内手続きを統一するための実務ガイドである。

> **重要:** 本書は一般的な実務指針であり、法的助言ではない。個別案件では、対象物の正確なライセンス本文、利用形態、契約、適用法を確認する。判断に迷う場合や「要確認」に該当する場合は、公開・納品・提供の前に法務／知財担当へ相談する。

### まず押さえる5原則

1. **公開されているだけではOSSではない。** OSI承認ライセンス等による明示的な許諾が必要で、ライセンス不明のコードは原則として利用しない。
2. **「無料」と「自由に利用可能」は別である。** 無料でも、商用利用、改変、再配布、利用者数等に制限があり得る。
3. **ライセンス名だけでなく利用形態で義務が決まる。** 社内実行、社外配布、顧客環境への納品、SaaS、改変、静的リンク等を確認する。
4. **OSS利用は著作権を放棄させるものではない。** 許諾条件を守ることで、複製・改変・配布等が認められる。
5. **採用時から記録する。** リリース直前の調査だけでは、推移的依存関係、同梱物、改変履歴、正確なソース対応が追えない。

## 2. 用語

| 用語 | 本書での意味 |
|---|---|
| OSS | OSIのOpen Source Definitionに適合するライセンスで提供されるソフトウェア |
| プロプライエタリ | 利用・改変・再配布等を権利者が独自条件で制限するソフトウェア |
| ソースアベイラブル | ソースは閲覧できるが、用途・競合・商用利用等の制限によりOSSとは限らないもの |
| 利用許諾 | 権利者が、条件の範囲内で著作物の利用を認めること |
| 配布／提供 | 複製物を組織外の第三者へ渡すこと。本書では販売、無償配布、納品、端末・機器への搭載、コンテナイメージの提供等を含めて広く扱う |
| コピーレフト | 配布等の際、対象となる改変物・派生物にも同じライセンスやソース提供を求める仕組み |
| SBOM | Software Bill of Materials。ソフトウェアを構成する部品と依存関係の記録 |
| SPDX ID | `MIT`、`Apache-2.0`、`GPL-3.0-only`等の標準化されたライセンス識別子 |

日本の著作権法上、著作権者は利用を許諾でき、利用者は許諾された方法・条件の範囲で利用できる。ライセンス条件は「お願い」ではなく、利用可能な範囲を定める基礎として扱う。

## 3. 最初に確認する判断フロー

```text
対象物を採用したい
  ├─ ライセンスと権利者を特定できない → 原則採用しない／法務確認
  ├─ 独自・商用・ソースアベイラブル条件 → 契約全文を確認／法務確認
  └─ 標準的なOSSライセンス
       ├─ 組織内だけで使用 → 告知等を保管。AGPLや契約上の例外も確認
       └─ 組織外へ提供、またはネットワークサービスで使用
            ├─ Permissive → 著作権表示・ライセンス・NOTICE等を同梱
            ├─ Weak copyleft → 対象ファイル／ライブラリとリンク条件を確認
            ├─ Strong copyleft → 結合物を含む対応ソースと同一ライセンスを確認
            └─ Network copyleft → ネットワーク利用者へのソース提供も確認
```

「組織外」には、顧客、委託先、取引先、別法人、一般利用者を含む。グループ会社は別法人であり、当然に社内利用扱いになるとは限らない。委託契約、秘密保持契約、アクセス制限があっても、ライセンス上の提供該当性が自動的に消えるわけではない。

## 4. 主なライセンスの分類と実務対応

以下は代表的な傾向であり、例外、追加条項、デュアルライセンス、版の違いが優先する。

| 分類 | 代表例（SPDX ID） | 主な義務・特徴 | 原則的な社内判断 |
|---|---|---|---|
| Permissive | `MIT`、`BSD-2-Clause`、`BSD-3-Clause`、`ISC` | 著作権表示とライセンス文の保持が中心。改変・商用利用・プロプライエタリ製品への組込みが可能 | 通常利用可。配布物の第三者告知へ収録 |
| Permissive＋明示的特許許諾 | `Apache-2.0` | LICENSE保持、変更表示、該当するNOTICE内容の保持。寄与者からの特許許諾と一定の特許訴訟時の終了条項 | 通常利用可。NOTICEと変更記録を確認 |
| ファイル単位のWeak copyleft | `MPL-2.0` | MPL対象ファイルの改変を配布する場合、そのファイルのソースをMPLで提供。別ファイルの独自コードまで一律には及ばない | 対象ファイルを分離・追跡できる場合に利用可 |
| ライブラリ単位のWeak copyleft | `LGPL-2.1-only`、`LGPL-3.0-only` | LGPL部分とその改変のソース提供に加え、利用者がライブラリを差し替え／再リンクできる条件等が問題になる | 動的／静的リンクだけで機械的に判断せず、リンク方法と配布形態を審査 |
| Strong copyleft | `GPL-2.0-only`、`GPL-2.0-or-later`、`GPL-3.0-only` | 対象プログラムまたはそれに基づく結合物を配布する場合、対応ソースの提供とGPLでの許諾が必要になり得る | 独自製品への組込み・リンク・派生物は要確認。独立プログラムとしての利用も境界を記録 |
| Network copyleft | `AGPL-3.0-only` | GPL型の義務に加え、改変版をネットワーク越しに利用させる場合、利用者に対応ソース取得機会を提供 | SaaS、Web、API、社外ユーザー利用は原則法務確認 |
| Public domain相当／権利放棄型 | `Unlicense`、`0BSD` | 条件は非常に少ないが、法域ごとの権利放棄の有効性、特許・商標等は別問題 | 出所と版を記録し、重要部品は特許条項も確認 |
| 非OSS・独自条件 | SSPL、各種BSL、Elastic License、Commons Clause、研究限定・非商用ライセンス等 | 用途、競合サービス、商用利用、提供形態、一定期間後のライセンス変更等を個別に制限 | OSSとして扱わない。採用前に契約・法務確認 |

### よくある義務の意味

- **著作権表示・ライセンス文の保持:** バイナリだけを配布する場合も免除とは限らない。アプリ内の「オープンソースライセンス」、同梱ファイル、製品マニュアル等、受領者が確認できる場所へ掲載する。
- **NOTICE:** Apache-2.0の依存物にNOTICEがある場合、ライセンス本文の条件に従い、該当する帰属表示を読みやすい形で引き継ぐ。NOTICEへ無関係な情報を機械的に混ぜない。
- **対応ソース:** 実際に配布したオブジェクトコードを生成するためのソース、ビルド用スクリプト等を含み得る。上流URLの案内だけ、差分だけ、別バージョンのソースだけでは不十分になり得る。
- **同一ライセンス:** コピーレフト対象を、受領者にも同じ自由を与える条件で提供する。独自のNDAや再配布禁止を対象コードへ上乗せできない場合がある。
- **特許:** 著作権の利用許諾と特許許諾は同じではない。Apache-2.0等は明示的な特許条項を持つが、すべてのOSSライセンスが同等の許諾を含むわけではない。
- **商標:** OSSライセンスは通常、プロジェクト名・ロゴの商標利用まで許諾しない。自社製品名、広告、互換性表示は別途確認する。

## 5. 利用形態別の注意点

| 利用形態 | 典型的な確認事項 |
|---|---|
| 開発ツールとして実行 | 成果物へコードが混入しないか、テンプレート／生成コードのライセンス、プラグインや商用版の利用条件 |
| 社内サーバー・社内端末 | 原則として配布時の義務は発生しにくいが、AGPL、外部常駐者、別法人、契約条項を確認 |
| SaaS／Web／API | 通常のGPLはネットワーク利用だけで配布義務が発生するとは限らない。一方、AGPL、SSPL、独自SaaS制限は要確認 |
| 顧客へのバイナリ納品 | LICENSE、著作権表示、NOTICE、対応ソース、再許諾条件をリリース物と契約の両方で確認 |
| コンテナ／VM／機器への搭載 | OSパッケージ、ベースイメージ、CLI、フォント等も提供物に含まれる。アプリ依存関係だけを調べない |
| モバイル／デスクトップ配布 | アプリストア規約、DRM、署名、再リンク可能性とコピーレフト条件の両立を確認 |
| ソースコードのコピー・改変 | スニペットでも著作物性があれば対象。元ファイルのヘッダー、変更表示、履歴を保持 |
| 別プロセス・API・IPC連携 | 物理的な分離だけで非派生物とは断定できない。通信方式、密結合性、同時配布、設計上の独立性を記録 |
| 顧客指定OSS／受託開発 | 顧客指定でも自社の遵守責任がなくなるとは限らない。成果物の権利保証・補償条項との整合を確認 |

### 「社内利用」の境界

通常、単一法人内で複製して使用するだけならGPL系の配布条件は発動しにくい。一方、別法人への移転、顧客環境へのデプロイ、端末貸与、成果物の引渡しは個別判断が必要である。クラウド事業者へ実行環境を置く場合も、事業者が単に自社のために処理するのか、複製物を受領・利用するのかを契約と構成から確認する。

## 6. ソフトウェア以外のライセンス

| 対象 | 注意点 |
|---|---|
| ドキュメント・画像・動画 | Creative Commons（CC）等を確認。`BY`は表示、`SA`は同一条件、`NC`は非商用、`ND`は改変禁止。NC／ND付きはOSSではない |
| データ・データベース | `CC0-1.0`等が使われる。著作権だけでなく、データベース権、個人情報、利用規約、取得元との契約、営業秘密を確認 |
| フォント | `OFL-1.1`等。埋込み、改変、フォント単体の再配布、予約名称の条件を確認 |
| AIモデル・重み | コード、モデル重み、学習データ、出力の条件は別々に確認。「Open」「Open Weight」という名称だけでOSSと判断しない |
| API・クラウドサービス | SDKのOSSライセンスとは別に、API利用規約、データ利用、再販売、レート制限、地域、終了条件を確認 |
| 規格・サンプルコード | 規格文書の著作権、実装に必要な特許、サンプル固有のライセンスを確認 |

## 7. 採用から廃止までの標準プロセス

### 7.1 採用申請

担当者は、直接依存・コピーしたコード・ビルド時取得物について最低限次を記録する。

| 項目 | 記録例 |
|---|---|
| コンポーネント | パッケージ名、配布元、公式URL |
| 特定情報 | バージョン、コミット、ハッシュ、取得日 |
| ライセンス | SPDX ID、LICENSE／NOTICEの原文、例外・追加条件 |
| 利用方法 | 実行のみ、改変、リンク、コピー、同梱、SaaS等 |
| 提供範囲 | 社内のみ、顧客、一般配布、別法人、対象地域 |
| 改変 | 有無、変更ファイル、パッチ保管先 |
| 依存関係 | 推移的依存、バンドル済みコード、ベースイメージ |
| 判断 | 許可、条件付き許可、法務確認、禁止。判断者と日付 |

次の場合は、自動承認にせず法務／知財担当へエスカレーションする。

- ライセンスなし、不明、独自ライセンス、複数ライセンスの選択条件が不明
- GPL／LGPL／AGPL等を独自製品・SaaS・機器へ組み込む
- ソースアベイラブル、非商用、研究限定、競合・用途・地域制限がある
- 複数ライセンスの互換性、リンク、派生物性、プラグイン境界に疑義がある
- コードの権利者、取得元、再配布権限に疑義がある
- 特許、商標、暗号、輸出管理、個人情報等のライセンス外リスクがある
- 顧客契約の権利保証、秘密保持、ソース非開示条件と衝突する可能性がある

### 7.2 開発中

- ロックファイルを使用し、依存関係とバージョンを再現可能にする。
- SCA（Software Composition Analysis）等で直接・推移的依存を継続検査する。
- `LICENSE`、`COPYING`、`NOTICE`、各ファイルのヘッダー、パッケージメタデータを確認する。リポジトリ画面のライセンス表示だけに依存しない。
- GPL系の `-only` と `-or-later`、例外条項（例: Classpath exception）を区別し、SPDX式で記録する。
- コピーしたソースと改変箇所を追跡し、上流のライセンス表示を削除しない。
- バージョン更新時はライセンス変更、権利者変更、依存関係追加を再審査する。

### 7.3 リリース判定

リリース責任者は次を確認し、証跡を保管する。

- [ ] 最終成果物を基準にSBOM／依存関係一覧を生成した
- [ ] 未特定ライセンス、禁止ライセンス、未承認コンポーネントがない
- [ ] `THIRD_PARTY_NOTICES`等に必要な著作権表示・ライセンス文・NOTICEを収録した
- [ ] コピーレフト対象、改変箇所、提供すべき対応ソースを特定した
- [ ] ソース提供方法、提供期間、問い合わせ窓口を決めた
- [ ] インストーラー、コンテナ、機器、ドキュメント、フォント、Web資産も検査した
- [ ] 製品EULA、顧客契約、アプリストア規約がOSSの権利を制限していない
- [ ] 承認記録、SBOM、スキャン結果、配布した表示・ソースの写しを保存した

### 7.4 運用・廃止

- 脆弱性対応と同じく、ライセンス変更や違反通知を追跡する。
- 削除した依存関係も、過去リリースの証跡と対応ソースは社内保存基準に従い保持する。
- 違反の疑いを発見した場合は、証拠を保全し、配布拡大を止め、法務／知財担当と是正する。独断で権利者へ回答しない。

## 8. 第三者ライセンス表示のひな型

実際のライセンス条件が要求する全文・形式を優先する。以下は管理用の最小例である。

```text
Third-Party Software Notices

Component: <name>
Version: <version or commit>
Source: <official source URL>
Copyright: <copyright notice from upstream>
License: <SPDX identifier>
Modifications: <none / summary and date>

<required license text and applicable NOTICE content>
```

対応ソースを提供する場合は、対象製品・バージョンとの対応、取得方法、提供期限、連絡先を明記する。Web上で提供する場合も、リンク切れや認証期限によって受領者が取得不能にならないよう運用する。

## 9. よくある誤解

| 誤解 | 正しい考え方 |
|---|---|
| GitHubに公開されているから自由に使える | ライセンスがなければ、原則として複製・改変・再配布の許諾はない |
| OSSは商用利用できない | OSI準拠のOSSは商用利用を排除しない。ただし配布時の条件等は守る |
| 無料のパッケージはOSSである | 無料配布とOSSは別。利用規約や独自ライセンスを確認する |
| 著作権表示を入れれば何でも使える | 表示は義務の一部にすぎず、ソース提供や同一ライセンス等が必要な場合がある |
| 改変しなければ義務はない | 未改変でも、配布時にライセンス文・著作権表示・ソース提供等が必要な場合がある |
| 動的リンクならGPL／LGPLの問題はない | リンク方式は一要素。ライセンスの版、結合状態、再リンク可能性、配布形態を総合確認する |
| SaaSならすべてのOSSでソース公開不要 | AGPL等はネットワーク越しの利用にも条件を課す。独自ライセンスにもSaaS制限がある |
| 社内で使えば何でも安全 | 契約、AGPL、別法人、外部委託、情報セキュリティ等の論点は残る |
| SBOMを作れば遵守できる | SBOMは在庫情報であり、条件の解釈、表示、ソース提供、承認の実行が別途必要 |

## 10. 自社コードを公開する場合

1. 会社が公開権限を持つことを確認する。従業員・委託先の権利帰属、第三者コード、秘密情報、特許出願予定を点検する。
2. 公開目的に合う、既存の標準ライセンスを選ぶ。独自ライセンスの作成は互換性と解釈コストを増やすため、法務判断なしで行わない。
3. リポジトリ直下に正確な `LICENSE` を置き、必要に応じて `NOTICE`、`README`、各ファイルのSPDX IDを整備する。
4. コントリビューションの扱い（DCO、CLA、規約）、行動規範、セキュリティ窓口を決める。
5. 商標の利用条件、サポートや保証の有無をライセンスと混同せず明記する。

一般に、広い再利用を優先するならMIT／Apache-2.0等、改変の共有を求めるならMPL／GPL／AGPL等が候補になる。ただし、会社方針、特許戦略、既存依存物との互換性、ビジネスモデルから決定する。

## 11. 部署内の推奨管理ルール

- ライセンス表記は可能な限りSPDX IDで統一し、推測値と確認済み値を区別する。
- 「許可リスト」はライセンス単体の無条件許可ではなく、利用形態と義務を組み合わせて定義する。
- 禁止・要審査ルールは、開発端末、CI、リポジトリ、リリース工程で同じ基準を使う。
- SBOMはSPDXまたはCycloneDX等の機械可読形式とし、製品・バージョンごとに追跡する。
- 自動スキャン結果は人がレビューする。誤検知、ライセンス例外、デュアルライセンス、コード同梱の有無は自動判定だけでは確定しない。
- 教育、役割分担、申請窓口、違反時の是正手順を文書化する。体制整備にはOSSライセンス遵守の国際規格ISO/IEC 5230（OpenChain）も参考にする。
